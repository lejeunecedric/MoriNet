<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| owner form POST → vaults row | Free-form theme/checkbox values cross into persisted per-vault state that plan 12-03 will render into served HTML |
| migration → existing DBs | ALTER TABLE runs against live SQLite data at boot |
| store row → Vault struct | DB values flow into every handler that reads a vault |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-06 | Tampering | theme form value | mitigate | Server-side whitelist `""|light|navy|rust|coal|ayu` with REJECT (error_page), not coercion — nothing but one of six fixed tokens ever reaches the DB, so plan 12-03's string rewrite can never carry attacker content (no XSS, no path traversal) |
| T-12-07 | Tampering | edit form CSRF/impersonation | mitigate | Persistence runs strictly after the existing `can_edit_vault` owner gate and plan 12-01's `is_locked` gate; a non-owner/locked POST never reaches the store calls |
| T-12-08 | Denial of service | migration 0009 | mitigate | Two additive `ADD COLUMN ... NOT NULL DEFAULT` statements — SQLite handles them in-place, no table rewrite of content, existing rows get safe defaults (0 / "") |
| T-12-09 | Information disclosure | theme value in HTML | accept | Theme is the owner's own choice rendered only on their vault's pages; whitelist bounds it to five mdBook built-in names |
| T-12-SC | Tampering | dependencies | accept | No new dependencies in this plan |

Block-on-high: any newly discovered HIGH threat in touched code blocks the plan. ASVS L1 applies.
