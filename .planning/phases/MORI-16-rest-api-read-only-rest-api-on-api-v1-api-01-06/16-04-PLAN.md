<objective>
Add the per-token fixed-window rate limiter (API-06, D-13): an in-process counter map on `AppState` following the `vault_locks` precedent, enforced inside the `/api/v1` Bearer middleware, answering over-limit requests with 429 problem+json + `Retry-After`. </objective>

- Discretion decisions made by planner (executor follows):
  - **Data structure (locked):** `pub api_rate: std::sync::Mutex<std::collections::HashMap<String, (u32, u64)>>` on AppState — value `(count, window_start_unix_secs)`; key = lowercase hex SHA-256 of the plaintext bearer token (sha2 + hex already deps via the etag_of/token_hash precedent — see `token_hash` server.rs:1457-1463 style). std Mutex guards ONLY the map; get-or-insert + increment happen synchronously before any await, mirroring `vault_lock` (server.rs:47-56) including the `.expect("api_rate map mutex poisoned")` style.
  - **Window semantics:** fixed window — on check: if `now - window_start >= 60` reset count to 1 and window_start to now; else count += 1; over-limit when count > 120. `Retry-After = 60 - (now - window_start)` seconds (integer, ≥1, ≤60).
  - **Pruning (memory bound):** on every check, while holding the lock, retain entries whose `window_start + 60 >= now` (i.e. drop windows fully expired) — map size is bounded by distinct tokens active in the last 60 s. No background task, no deps.
  - **Placement:** enforcement runs in `require_api_bearer` AFTER successful token resolution (so unauthenticated floods aren't tracked — they cost one indexed query and no map entry) and BEFORE the handler runs; the public docs page (16-05) is outside the Bearer group and therefore uncounted — consistent with decision 6a ("all /api/v1 [API] endpoints count equally"; static HTML is not an API endpoint).
  - **Constant:** `const API_RATE_LIMIT: u32 = 120; const API_RATE_WINDOW_SECS: u64 = 60;` in api.rs. Tests may not change the constant; the 429 test loops 121 requests against test_router (cheap: in-memory store, oneshot).
</context>

<threat_model>
  <threat stride="Denial of Service" severity="high">
    Unbounded rate-limiter map growth: an attacker cycling forged/rotated tokens could balloon a naive HashMap into OOM. Mitigation: entries are keyed by fixed-size token hash, created ONLY after successful token verification (forged tokens never insert), and every check prunes windows expired ≥ 60 s — map size is bounded by distinct VALID tokens active in the last minute; `rate_limiter_prunes_expired_windows` pins it.
  </threat>
  <threat stride="Information Disclosure" severity="high">
    Token leakage (B2): using the plaintext token as map key or including it in the 429 detail/log would expose credentials to memory dumps, panics, or logs. Mitigation: SHA-256 hex key (one-way), fixed generic detail string, zero logging (no tracing dep); test asserts key is 64-hex ≠ plaintext.
  </threat>
  <threat stride="Denial of Service" severity="medium">
    Limiter as its own DoS (lock contention / held lock across await): holding the std Mutex across an await would serialize or deadlock the whole API. Mitigation: check is a pure synchronous fn completing before `next.run(...).await`, same contract as vault_locks (server.rs:38-40 comment); pruning is O(map size) with map bounded as above.
  </threat>
  <threat stride="Spoofing" severity="medium">
    Rate-limit evasion by token rotation: a user with many tokens multiplies budget. Accepted for v1 — token minting is self-service but account-scoped and revocable on /account; per-USER budgets are a policy knob out of D-13's scope (per-token is the locked requirement). Recorded, not mitigated.
  </threat>
  <threat stride="Repudiation" severity="low">
    Clock source: limiter uses the same unix_now() as session expiry; monotonic-vs-wall-clock skew at window boundaries can shift a window by the NTP adjustment size — bounded, non-security-relevant for a 120/min soft limit.
  </threat>
</threat_model>
