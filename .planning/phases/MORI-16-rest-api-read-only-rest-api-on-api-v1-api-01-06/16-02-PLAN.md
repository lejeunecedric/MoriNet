<threat_model>
  <threat stride="Spoofing" severity="high">
    Cookie/Bearer mixing (B4): if the api group sat under `require_session`, a browser session cookie could authenticate the API (CSRF-shaped) or the two auth systems could disagree. Mitigation: standalone merged group with its own route_layer (16-PATTERNS open flag #4); middleware reads ONLY the AUTHORIZATION header; test `api_ignores_session_cookie` pins both directions.
  </threat>
  <threat stride="Information Disclosure" severity="high">
    Token leakage (B2): echoing the submitted token in a 401 detail, or logging headers, would leak credentials into logs/proxies. Mitigation: fixed detail string (no echo), zero logging in api.rs (grep gate), problem+json bodies carry only type/title/status/detail/code.
  </threat>
  <threat stride="Information Disclosure" severity="medium">
    Existence leak via 403-vs-404 or error-shape divergence (B1/D-02): a 403 or a non-problem 404 would confirm vault/route existence outside the ACL. Mitigation: single `problem()` constructor for every error path including middleware 401 and router fallback 404; unknown paths and (wave 3) invisible vaults both answer `not_found`.
  </threat>
  <threat stride="Denial of Service" severity="low">
    Unauthenticated probe flood on the 401 path: accepted for v1 — the lookup is one indexed SQLite query and the rate limiter (16-04) covers authenticated traffic; no unauthenticated data endpoint exists (docs page in 16-05 is static).
  </threat>
</threat_model>
