  <threat id="T-19-10" stride="Tampering" severity="medium">
    Stored XSS: MCP args/excerpts originate from note content and tool input, search queries and paths from arbitrary user input — all interpolated into the owner's Statistics page, where a script payload would execute in the highest-privileged session on the instance. Would be HIGH without mitigation; residual severity medium. Mitigation: html_escape on EVERY interpolated field (house rule T-10.1-09, same rule as the Wiki-changes section), no raw-HTML passthrough anywhere in the new fragments. Tests: stats_mcp_activity_escapes_untrusted (script/img payload pinned escaped).
  </threat>
  <threat id="T-19-11" stride="Information Disclosure" severity="medium">
    The detailed sections leak vault reading/searching behavior (who read what, what was searched) to viewers who should only see their own count — the exact info the stats page must not leak (STAT-05 ACL clause). Mitigation (D-05): both sections render strictly inside the existing `entry.personal || is_admin` branch; sharee and 403 paths untouched; actor emails shown only to owner/admin, consistent with existing per-user counts. Tests: stats_sharee_no_detailed_sections, stats_unrelated_user_forbidden (pre-existing, stays green).
  </threat>
  <threat id="T-19-12" stride="Tampering" severity="low">
    A crafted ?days= value (huge number, SQL fragment, non-numeric) could skew or attack the window queries. Mitigation: stats_days is a strict three-value whitelist with 90 fallback — the value reaching SQL is always one of three bound integers; store side additionally binds it as a parameter, never concatenates. Tests: stats_days_whitelist includes an injection-shaped input.
  </threat>
