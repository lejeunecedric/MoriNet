<threat_model>
  <!-- ASVS L1 (config: security_asvs_level=1); gate blocks on HIGH severity. -->
  <threat id="T-19-07" stride="Information Disclosure" severity="medium">
    Logging denied REST requests would write per-vault probing trails (and could turn the stats page into an existence oracle for slugs a caller may not see). Mitigation: every log call sits strictly AFTER the 404-collapse ACL gate (api_read_note Ok-collapse, api_search Ok arm) — problem+json early returns (400/404) write nothing; the fan-out only iterates the caller's OWN accessible vaults. Tests: api_denied_call_logs_nothing, api_search_requires_q_logs_nothing.
  </threat>
  <threat id="T-19-08" stride="Denial of Service" severity="low">
    A failing/slow access_log or search_queries insert on the hot API path could add latency or error out note reads and searches. Mitigation (STAT-05): tokio::spawn best-effort with dropped errors, response construction fully independent of logging (proven log_web_access contract); 90-day prune (19-01) bounds table size. Tests: all pre-existing api response-shape tests (raw markdown, meta JSON, ETag/304) stay green untouched.
  </threat>
  <threat id="T-19-09" stride="Tampering" severity="low">
    Raw query text stored from user input could carry control characters or oversized payloads into search_queries. Mitigation: the query is stored as bound TEXT (parameterized INSERT — no SQL injection surface), trimmed and non-empty-validated before the handler reaches the log call (api.rs:485-491), and the display layer (19-04) html-escapes it; table growth is bounded by the 90-day prune. Tests: api_search_logs_access_and_query pins the stored shape.
  </threat>
</threat_model>
