<threat_model>
  <!-- ASVS L1 (config: security_asvs_level=1); gate blocks on HIGH severity. -->
  <threat id="T-19-04" stride="Information Disclosure" severity="medium">
    mcp_activity rows persist note-content excerpts and raw tool args (paths, queries) at rest — bulk exposure of vault prose to anyone who can read the table. Mitigation (D-01/D-05): excerpt hard-capped at 200 chars by truncate_chars before any insert, resp_size is a number not content, full bodies never stored (no schema column for them), 90-day prune (19-01), and the only read path is the owner/admin-gated Statistics section (D-05, 19-04). Tests: mcp_read_note_logs_activity pins the 200-char cap shape.
  </threat>
  <threat id="T-19-05" stride="Spoofing" severity="medium">
    A caller probing vaults they cannot access could plant rows in a victim vault's activity feed (fake "actor X read your vault" noise) or leak vault existence through logging. Mitigation: detailed rows are written ONLY on ACL-passing Ok arms — every Err arm (including collapsed invisible-vault NotFound) writes nothing, so denied probes leave zero trace in any vault's table; actor identity is the authenticated token email, not caller input. Tests: mcp_denied_call_logs_no_activity.
  </threat>
  <threat id="T-19-06" stride="Denial of Service" severity="low">
    A slow or failing mcp_activity insert could add latency to or fail tool responses. Mitigation (STAT-05): tokio::spawn fire-and-forget with the error dropped — identical contract to the proven log_access (mcp.rs:201); the tool response is constructed independently of logging. Tests: all existing mcp pins stay green with logging wired.
  </threat>
</threat_model>
