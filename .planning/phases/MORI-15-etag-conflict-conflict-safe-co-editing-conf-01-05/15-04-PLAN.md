<objective>
Turn same-slug re-upload of an owned uploaded vault into the update path
(D-01/D-04) with a per-file hash-compare conflict gate (D-02): stale trees are
rejected with a rich JSON conflict response (409), an explicit `force=1`
re-submit overwrites and records `modified`/`forced=1` rows in vault_changes
(D-05/D-06). Plain new-vault uploads behave exactly as before (CONF-05).
</objective>

<context>
- Phase context: 15-CONTEXT.md D-01, D-02, D-04, D-05, D-06; Phase 14 gate
  order must be reused (locked → name → quota → create; update mirrors it minus
  quota/create).
- 15-PATTERNS.md §5 §6 §10; FEATURES.md upload conflict UX (reject+list, never
  silent overwrite, force escape hatch).
- Planner decisions (recorded, executor follows):
  - Conflict response: HTTP 409, `application/json`:
    `{"status":"conflict","vault":"<slug>","conflicts":[{"path":"a.md",
    "server_etag":"\"<hex>\"","changes":[{"ts":"...","kind":"modified",
    "actor":"user@example.com"}]}]}` — `changes` from
    `store.vault_changes_for_path(slug, path, 5)` (D-07 data).
  - Staging: update streams parts to `data_dir/uploads/.staging/<uuid4>/`
    (same sanitization + caps as the live path), compares, then writes live
    files via `webdav::write_source_atomic` under the per-vault lock; staging
    dir is removed on every exit path. `fail_upload`'s tree-wipe is NOT reused
    on the live tree (PATTERNS §5 warning).
  - Conflict = present on both sides with different sha256 (D-02). Local-only =
    added; server-only = untouched, force never deletes (D-02).
  - Audit: one `event_id` per update operation; overwritten files kind
    `modified`, local-only files kind `added`, `forced = force_flag`,
    `actor = claims.email` (D-05/D-06); best-effort spawn + eprintln swallow.
  - Success response on update = same `Redirect::to("/vault/{slug}/")` as the
    new-vault path (fetch follows the redirect; JS treats non-409 as success).
  - Non-JS fallback: none beyond the unchanged server API (plain multipart POST
    with a `force` text field still works from curl); the two-phase fetch flow
    (15-05) is the primary and only browser UX, per D-03 discretion.
</context>

<threat_model>
  <abuse case="path traversal via upload parts (update path)">
    Staged writes reuse the Phase 14 sanitization verbatim: rel-path rejection
    plus `parent.canonicalize().starts_with(staging_root)` before any byte is
    written; live writes go to `uploads/&lt;slug&gt;/&lt;rel&gt;` where rel was
    validated against the staging root and slug is server-derived
    (`vault_slug_from_name`). Mitigation: traversal test extended to the update
    path (409/400 before any write).
  </abuse>
  <abuse case="ownership bypass — update someone else's vault / git vault">
    Update_mode requires `vault_source == None` AND `owner_email ==
    claims.email`, checked before any staging write; locked-account gate stays
    first (D-04). Tests cover other-user and git-vault refusals.
  </abuse>
  <abuse case="force flag as precondition bypass">
    `force=1` only skips the conflict gate; it never skips locked/ownership/
    sanitization gates. Mitigation: acceptance asserts gate order (locked →
    eligibility → conflict gate).
  </abuse>
  <abuse case="info leak via conflict JSON">
    Conflict list exposes paths, ETags and actor emails — endpoint is
    owner-only (same gate), so the requester already owns the vault and can see
    its wiki-changes page. Mitigation: no conflict body for non-owners.
  </abuse>
  <abuse case="DoS / disk exhaustion via staging">
    Staging doubles disk use per update but is bounded by existing caps (2000
    files × 5 MB) and removed on every exit path (success, 409, error);
    hashing cost is linear over capped sizes. Mitigation: cleanup_staging on
    all paths + test asserts no `.staging` leftovers after each scenario.
  </abuse>
  <abuse case="TOCTOU between conflict compare and live write (C3/C4)">
    A WebDAV PUT could land between compare and write. Mitigation: the live
    write phase runs under the same per-vault lock as WebDAV PUT (15-03) and
    each file write is atomic; residual cross-order race at team scale is
    documented as accepted (FEATURES.md complexity note).
  </abuse>
</threat_model>
