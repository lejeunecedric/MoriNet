<objective>
Home-page UX: a "Load local" button beside "Load vault" (D-08) opening the
folder picker directly, name derived from the picked folder, and the two-phase
`fetch` upload flow (D-03) that renders the rich conflict list with per-file
wiki-changes links (D-07) plus an "Upload anyway" force re-submit — no
re-picking the folder.
</objective>

<context>
- Phase context: 15-CONTEXT.md D-03, D-07, D-08 (D-08 supersedes the Phase 14
  two-form layout: no name input, no "Upload vault" button for the local flow).
- 15-PATTERNS.md §8 §9: raw-string JS const (pitfall #25 — brace-bearing JS
  never inside `format!`), ES5 dialect (`var`/`function`, DOMContentLoaded),
  `app_page()` shell / existing panel+table classes only (Phase 9b: no new CSS).
- Planner decisions (recorded, executor follows):
  - FormData field order: `name` first, then `force` (only on phase 2), then
    files appended as `fd.append('files', file, file.webkitRelativePath)` so
    the server's top-dir strip (Phase 14 D-03) sees the same layout a native
    form upload sends.
  - Conflict rendering: JS injects into the existing panel using existing
    classes (`section.panel`, `table`, `tr`/`td`); every path/actor rendered
    via `textContent` (never innerHTML interpolation) — XSS-safe; each
    conflicting file row links to `/vault/{slug}/stats` (wiki-changes section).
  - Non-JS fallback: none — the server API stays plain-multipart (curl works);
    the page already depends on JS for other features (locked popup, count).
  - Success (non-409, fetch resolves after redirect) → `window.location` to
    `/vault/{slug}/` (slug taken from the derived name's slug or the response
    URL).
</context>

<threat_model>
  <abuse case="XSS via conflict list rendering (attacker-controlled file paths / actor emails)">
    Conflict paths come from a vault the attacker owns and actor emails are
    user-controlled. Mitigation: JS renders every dynamic value via
    `textContent` (never innerHTML interpolation); server already html_escape-s
    anything it renders; acceptance greps forbid innerHTML injection of
    conflict data.
  </abuse>
  <abuse case="CSRF / cross-origin abuse of /vaults/upload via fetch">
    Same-origin `fetch` with default credentials mirrors the existing
    cookie-auth form POST — no new surface or weaker posture than Phase 14;
    ownership + locked gates server-side remain the boundary (T-12-01 style:
    JS is UX only). Mitigation: no client-side trust; force flag re-checked
    server-side per 15-04 gates.
  </abuse>
  <abuse case="path traversal via client-derived name/filename">
    `webkitRelativePath` only shapes the multipart filename; the server's
    existing sanitization (15-04, unchanged Phase 14 pipeline) rejects
    traversal before any write. Mitigation: 15-04 traversal tests cover the
    update path.
  </abuse>
</threat_model>
