## What was built

All changes in `src/mcp.rs` (plan scope; no store changes needed).

### Task 1 — Best-effort access_log wiring (4 tools)
- Private helper `MoriMcp::log_access(slug, path)`: clones `store` + `email`, `tokio::spawn`s `let _ = store.log_access(&email, slug, "mcp", path).await` — a failing/slow insert can never fail a tool call (same contract as web plan 02).
- Call sites, each after the ACL/safe_join gate and only on the success path:
  - `list_vaults` → `(slug='-', path='-')`
  - `list_notes` → `(slug, path = requested sub-path or '-')`
  - `read_note` → `(slug, note path)`
  - `search_notes` → one row per vault actually searched (`path='-'`; slug-scoped query = one row)
- Denied calls (`source_dir` None, invalid path, missing note/folder) log nothing — no existence leak into the log.

### Task 2 — Share-ACL proof at the tool surface
Four tests on plan 01's share union (they pass without any code change — that is the point: the union is real on the MCP surface too, pitfall #14):
- `mcp_sharee_sees_shared_vault` — reader share lists with role `read`, writer share with role `write`; both read + list notes via a sharee-bound `MoriMcp`.
- `mcp_hidden_share_invisible` — after `hide_share`: absent from `list_vaults`, `read_note` returns the exact generic `"vault not found or access denied"`.
- `mcp_revoked_share_denied` — access works, `revoke_share`, next call is the same generic error and the vault is gone from `list_vaults`.
- `mcp_search_finds_notes_in_shared_vault` — slug-less `search_notes` hits the shared vault's content.
Each test builds its own store + tmpdir + slug (pitfall #23).

## Deviations

## Decisions
- `search_notes` logs per vault in the searched set (before the cap can truncate hits), matching "one row per vault it actually searched".
- Logging placed strictly on success paths so error results are byte-for-byte unchanged.
- Tests query `access_log` directly via `sqlx` instead of adding a read API to `Store` (stats primitives already exist for production consumers).

## Lessons
- Polling for "any row" in a shared table is flaky when an earlier call already logged; poll for the specific expected tuple.
- The patch-tool's standalone rustc lint runs edition 2015 and floods false E0670 errors on this crate — trust `cargo test`/`clippy` instead.
