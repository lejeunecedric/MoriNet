<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → share/edit/stats handlers | untrusted form fields (emails, names, URLs) reach the store and later the HTML |
| sharee → owner-only surfaces | Edit and full Stats must not leak to sharees |
| request path → access_log | attacker-controlled path strings are stored and later rendered in Top pages |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10.1-06 | Elevation of privilege | share/edit POST handlers | mitigate | every mutating handler re-checks can_share / owner gate server-side (tests assert 403 for sharee) |
| T-10.1-07 | Information disclosure | stats visibility split | mitigate | sharee branch renders only the own-count line; negative test asserts owner labels absent |
| T-10.1-08 | Information disclosure | pending hint | accept | shown only to the owner/admin who typed the address — no cross-user enumeration |
| T-10.1-09 | Tampering (XSS) | share list + stats tables | mitigate | html_escape on every email, name, path interpolated into HTML; `share_page_escapes_email` test |
| T-10.1-10 | Denial of service | fire-and-forget log spawn flood | accept | inserts are cheap and indexed; 90-day prune (plan 01) bounds growth; logging never blocks the response |
| T-10.1-11 | Spoofing | CSRF on POST share/edit | accept | matches the app's existing same-site cookie posture (no CSRF tokens anywhere in the codebase today); HttpOnly + same-site cookie limits cross-site form posts; flag for a dedicated hardening phase if desired |
</threat_model>
