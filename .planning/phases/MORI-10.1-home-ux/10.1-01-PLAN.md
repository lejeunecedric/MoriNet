<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sharee → ACL | vault_shares rows change what a user can read/write across web, WebDAV and MCP |
| access_log rows → stats queries | attacker-controlled email/path strings later rendered on stats pages |
| boot → prune | unbounded table growth is a disk-exhaustion vector |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10.1-01 | Elevation of privilege | vault_shares.role | mitigate | CHECK (role IN ('reader','writer')) in migration + share_vault bails on any other role; writer never reaches admin |
| T-10.1-02 | Information disclosure | share to unknown email | accept | LOCKED decision: pending shares allowed; no enumeration signal is returned by the store (plan 02 shows the pending hint only to the vault owner, who supplied the address) |
| T-10.1-03 | Tampering | SQL injection in new queries | mitigate | every new query is parameter-bound via sqlx .bind(); no string-formatted SQL |
| T-10.1-04 | Denial of service | access_log unbounded growth | mitigate | 90-day prune at boot (this plan) + indexes keep aggregation queries bounded (LIMIT 90 / LIMIT 10) |
| T-10.1-05 | Spoofing | hidden flag abuse | accept | hidden only hides the row for the sharee who owns it; it never grants access and the owner can re-share (upsert clears hidden) |
</threat_model>
