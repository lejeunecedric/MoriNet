    - "Every membership change is logged to auth_events: additions kind 'group_sync', removals/demotions kind 'demote' (D-09 'demotions are logged'), actor + iss + sub + detail = group name; sync runs AFTER the session is minted and its errors are logged-and-swallowed — a sync failure never blocks sign-in and never half-applies silently"

<objective>
Implement the D-09/D-10/D-15 group sync in the SSO callback: parse the configured groups claim from the validated ID token, diff the user's memberships against the mapped managed set, apply adds/removes through the existing store surface, and log every change (demotions especially) to auth_events. This is the last functional block of the phase; the cross-cutting security matrix and docs land in 17-05.
</objective>

- Discretion decisions made by planner (executor follows, does not re-decide):
  - **New store helper (async sqlx):** `group_memberships_for_user(user_id) -> Result<Vec<(i64,String)>>` — the reversed join PATTERNS §5 says is missing: `SELECT g.id, g.name FROM groups g JOIN group_members m ON m.group_id = g.id WHERE m.user_id = ? ORDER BY g.name`. Plus `group_id_for_name(name) -> Result<Option<i64>>` (sync resolves mapping targets by name; unknown target group name → skip that entry + log deny detail `unknown_group_target` — a typo'd mapping must not silently create groups; `create_group` is NOT called by sync).
  - **Claim extraction:** from the already-validated `CoreIdTokenClaims` via `.extra()` (openidconnect exposes unregistered claims there as serde_json Values) keyed by `cfg.groups_claim`. Expected shape: JSON array of strings. Absent key → None (keep semantics). Present but wrong shape → treat as claim-invalid: skip sync entirely, log deny detail `groups_claim_invalid` (fail-closed: never act on garbage).
  - **Diff algorithm (locked):** managed_names = group_map.values().dedup(); resolve each to id (missing → skip + deny log). current = memberships of user ∩ managed ids. desired = for each (claim_value → target_name) in group_map where claim array contains claim_value → target id. adds = desired − current; removes = current − desired. Apply via add_group_member/remove_group_member (email-keyed API — pass the signed-in user's local email). Log each add kind `group_sync` detail `added:{group}`, each remove kind `demote` detail `removed:{group}`. No adds/removes → no log rows (keep the audit signal-to-noise).
  - **Admin safety net (D-10):** if any managed target group is the builtin `admin` group, membership changes there go through the SAME diff path — but the opt-in gate is the mapping itself: no mapping value == "admin" ⇒ `admin` is not in the managed set ⇒ claim can never touch it. Additionally refuse removal of the LAST admin (mirror ensure_default_memberships intent): if a removal would drop the admin group to zero members, skip that removal + log deny `last_admin_kept` (anti-lockout, D-07 spirit).
  - **Placement:** sync runs in the callback AFTER the session cookie is constructed and BEFORE the response is returned, as a best-effort block: `if let Err(e) = sync_groups(...).await { eprintln!(...) }` — sign-in succeeds regardless (vault_changes D-04 precedent), but every applied change is logged so the audit trail is complete.
  - **Provisioned users:** a freshly-provisioned reader starts in `free` only (17-03); `free` is only ever touched if explicitly mapped — default config never touches plan groups.
- Executor rules: no `--no-verify`; do NOT push; do NOT touch `.planning/STATE.md` or `.planning/ROADMAP.md`.

<threat_model>
  <threat id="T-17-16" stride="Privilege escalation" severity="high">
    A5 claim escalation: user self-serves an admin/privileged group by editing their IdP groups claim, or a claim smuggled via access token/userinfo is trusted. Mitigation: groups read ONLY from the JWKS-validated ID token's extra claims; admin group reachable only through an explicitly configured mapping value (opt-in); unknown mapping targets skipped, never auto-created; wrong-shape claim fails closed (skip + log). Tests: `group_sync_admin_mapping_absent_blocks_admin`, `group_sync_reads_only_id_token`, `group_sync_claim_wrong_shape_skips_and_logs`, `group_sync_unknown_target_group_skipped`.
  </threat>
  <threat id="T-17-17" stride="Integrity" severity="medium">
    Over-removal: sync strips manually-granted memberships or plan groups it was never configured to manage. Mitigation: managed set = mapping VALUES only (D-10); diff operates strictly within it; `free`/`admin` untouched unless explicitly mapped. Tests: `group_sync_never_touches_unmanaged_groups`, `group_sync_claim_present_empty_removes_managed` (removal scoped to managed only).
  </threat>
  <threat id="T-17-18" stride="Repudiation" severity="medium">
    Silent demotion: user loses group access with no audit trail (D-09 explicitly requires logging). Mitigation: every removal logs auth_events kind `demote` with actor/iss/sub/group; additions logged too; sync errors logged. Tests: `group_sync_claim_present_empty_removes_managed` (asserts the demote row), `group_sync_adds_mapped_groups` (asserts the group_sync row).
  </threat>
  <threat id="T-17-19" stride="Denial of Service" severity="medium">
    Admin lockout via sync: mapping misconfiguration or an emptied claim removes the last admin, stranding the instance (D-07 safety-net spirit). Mitigation: last-admin removal refused (`last_admin_kept`), and absent-claim-keeps-admin semantics mean an IdP outage/claim removal cannot demote. Tests: `group_sync_last_admin_kept`, `group_sync_admin_mapping_present_adds_and_absent_keeps`.
  </threat>
</threat_model>
