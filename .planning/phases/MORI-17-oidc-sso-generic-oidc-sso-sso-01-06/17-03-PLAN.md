<threat_model>
  <threat id="T-17-11" stride="Spoofing/Impersonation" severity="high">
    A1 email-takeover: attacker creates an IdP account with the victim's email and auto-links into the victim's local account (or an admin's). Mitigation: email is only ever a FIRST-LINK key, never a join key for returning users (iss,sub authoritative, D-03); email_verified strictly required (boolean true); admin accounts categorically refused (D-05); every link logged. Tests: `sso_returning_user_keyed_on_iss_sub_not_email`, `sso_admin_match_refused`, `sso_link_refused_when_email_not_verified`.
  </threat>
  <threat id="T-17-12" stride="Authorization bypass" severity="high">
    A7 gate bypass via auto-provision: anyone with an IdP account walks in as a provisioned user, or provisioning escalates beyond reader. Mitigation: exact-domain allowlist (no suffix match), empty allowlist ⇒ provisioning off, role hard-pinned to reader in `create_user_without_password` (assert), refusals create no rows. Tests: `sso_unmatched_domain_denied`, `sso_empty_allowlist_disables_provisioning`, `sso_auto_provisions_reader_for_allowed_domain` (asserts role == reader).
  </threat>
  <threat id="T-17-13" stride="Authentication" severity="high">
    Provisioned account gets a weak/known password (e.g. empty or email-derived) → password login becomes a side door around SSO policy. Mitigation: bcrypt over a random 2×uuid-v4 placeholder (128+ bits), never returned or logged; verify_login can never match it. Tests: `sso_provisioned_account_password_login_fails`, `create_user_without_password_placeholder_is_unguessable`.
  </threat>
  <threat id="T-17-14" stride="Integrity" severity="medium">
    Concurrent first-logins double-link one (iss,sub) or link-then-crash leaves a user with two identities. Mitigation: UNIQUE(provider,iss,sub) (0012) + INSERT OR IGNORE + re-read-on-conflict fallback; link and provision events logged so drift is auditable. Tests: `sso_link_race_falls_back_to_returning`, 17-01 `identity_unique_conflict_is_ignored`.
  </threat>
  <threat id="T-17-15" stride="Integrity" severity="medium">
    Case-variant emails create duplicate local accounts or link to the wrong row (the PATTERNS §11 divergence risk). Mitigation: single documented rule (trim + to_ascii_lowercase, LOWER() SQL, provisioned stored lowercase) applied at every SSO email touchpoint; divergence from password login documented in store.rs doc-comments and config docs (17-05). Tests: `sso_email_match_case_insensitive_link`, `user_by_email_normalized_matches_case_insensitively`.
  </threat>
</threat_model>
