<threat_model>
  <threat id="T-17-01" stride="Tampering/Availability" severity="medium">
    A partially-configured or blank-env `[oidc]` section half-enables SSO or crashes boot, taking password login down with it (SSO-05/SSO-06 violation). Mitigation: opt-in merge — never a hard error, blank-env ≠ shadow (Phase 12 precedent), partial ⇒ disabled + warning. Tests: `oidc_partial_config_disables_not_half_enabled`, `oidc_blank_env_does_not_shadow_file`, `oidc_absent_section_disables`.
  </threat>
  <threat id="T-17-02" stride="Integrity" severity="high">
    Without a DB-level uniqueness guarantee two users could end up linked to the same (provider, iss, sub) (or one identity to many users), letting one IdP account sign in as two local accounts. Mitigation: `UNIQUE(provider, iss, sub)` in migration 0012 + INSERT-OR-IGNORE helper semantics. Tests: `user_identities_migration_shape`, `identity_unique_conflict_is_ignored`.
  </threat>
  <threat id="T-17-03" stride="Availability" severity="high">
    Later OIDC waves silently break password login (cookie drift, middleware change, boot failure) — the exact A6/A7-adjacent regression D-08 exists to catch. Mitigation: this plan locks the behavior with the `sso_reg_*` suite BEFORE any OIDC code lands; every wave re-runs it. Tests: `sso_reg_password_login_mints_exact_session_cookie`, `sso_reg_password_login_wrong_password_401`, `sso_reg_bootstrap_admin_always_available`, `sso_reg_password_login_works_for_reader`.
  </threat>
  <threat id="T-17-04" stride="Information Disclosure" severity="medium">
    An audit table that stores tokens, codes, or full claims becomes a credential cache at rest. Mitigation: auth_events schema has NO token/code column — only kind/actor_email/iss/sub/detail; CHECK-locked kind vocab; 90-day prune. Tests: `user_identities_migration_shape` (column set asserted), `auth_events_check_rejects_unknown_kind`.
  </threat>
</threat_model>
