# PLAN 10-01 — API tokens (migration + store + /account page)

**Type**: vertical slice (DB → store → UI → tests). TDD mandatory.

## Objective

A logged-in user can create named API tokens on `/account` (plaintext value
shown only once), list them, and revoke them. Only the sha256 hash is stored.

## Changes

1. `migrations/0007_api_tokens.sql` — table `api_tokens(id, user_id FK CASCADE, name TEXT,
   token_hash TEXT UNIQUE, created_at INTEGER, last_used_at INTEGER NULL)`.
2. `src/store.rs` —
   - `create_api_token(user_id, name) -> (i64, String)` : 32 random bytes (rand),
     prefix `mn_` + hex ; stores sha256 hex ; returns the plaintext ONCE.
   - `list_api_tokens(user_id) -> Vec<ApiToken{id, name, created_at, last_used_at}>` (no hash).
   - `revoke_api_token(user_id, id) -> bool`.
   - `user_for_api_token(plain) -> Option<User>` : lookup by hash, updates `last_used_at`.
3. `src/server.rs` —
   - `POST /account/tokens` (form: name) → creates, re-renders `/account` with banner showing
     the plaintext once (via query flag or flash in-form).
   - `POST /account/tokens/revoke` (form: id) → revokes, redirects to `/account`.
   - "API tokens" section on `GET /account` : table (name, created, last used, Revoke
     button) + creation form. Go through `app_page()` (AD-12).

## Tests (RED first, in the existing store/server tests)

- `create_api_token` returns a `mn_…` plaintext ; the hash in the database matches the sha256 ;
  two creations yield distinct tokens.
- `user_for_api_token` : correct user for a valid token, `None` for an unknown token or
  after revocation ; `last_used_at` populated after use.
- `revoke_api_token` on a token belonging to ANOTHER user → false (no cross-user).
- Route: POST `/account/tokens` without a session → 401/redirect ; with a session → the plaintext
  appears in the HTML response once, then never appears again on GET `/account`.
- Revoke via the route removes the row.
