# PLAN 10-01 — API tokens (migration + store + page /account)

**Type**: vertical slice (DB → store → UI → tests). TDD obligatoire.

## Objectif

Un utilisateur connecté peut créer des tokens d'API nommés sur `/account` (valeur en clair
affichée une seule fois), les lister et les révoquer. Le hash sha256 seul est stocké.

## Changes

1. `migrations/0007_api_tokens.sql` — table `api_tokens(id, user_id FK CASCADE, name TEXT,
   token_hash TEXT UNIQUE, created_at INTEGER, last_used_at INTEGER NULL)`.
2. `src/store.rs` —
   - `create_api_token(user_id, name) -> (i64, String)` : 32 octets aléatoires (rand),
     préfixe `mn_` + hex ; stocke sha256 hex ; retourne le plaintext UNE fois.
   - `list_api_tokens(user_id) -> Vec<ApiToken{id, name, created_at, last_used_at}>` (sans hash).
   - `revoke_api_token(user_id, id) -> bool`.
   - `user_for_api_token(plain) -> Option<User>` : lookup par hash, met `last_used_at` à jour.
3. `src/server.rs` —
   - `POST /account/tokens` (form: name) → crée, re-render `/account` avec banner showing
     the plaintext once (via query flag ou flash in-form).
   - `POST /account/tokens/revoke` (form: id) → revoke, redirect `/account`.
   - Section « API tokens » sur `GET /account` : table (nom, créé, dernier usage, bouton
     Revoke) + formulaire de création. Passer par `app_page()` (AD-12).

## Tests (RED d'abord, dans les tests existants de store/server)

- `create_api_token` retourne un plaintext `mn_…` ; le hash en base correspond au sha256 ;
  deux créations donnent des tokens distincts.
- `user_for_api_token` : bon user pour un token valide, `None` pour un token inconnu ou
  après révocation ; `last_used_at` rempli après usage.
- `revoke_api_token` sur un token d'un AUTRE user → false (pas de cross-user).
- Route: POST `/account/tokens` sans session → 401/redirect ; avec session → le plaintext
  apparaît dans la réponse HTML une fois, puis n'apparaît plus sur GET `/account`.
- Revoke via la route retire la ligne.
