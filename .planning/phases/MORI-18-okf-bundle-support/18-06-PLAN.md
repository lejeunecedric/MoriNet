<threat_model>
  <threat id="T-18-15" stride="Information Disclosure" severity="high">
    A `type`/`tags` filter evaluated BEFORE or OUTSIDE ACL could confirm the existence/content structure of vaults the caller cannot read (oracle via filter-match counts on private vaults). Mitigation: filters run strictly on the Vec returned by the ACL-gated `crate::api::list_notes`/`search_notes` helpers; inaccessible vaults never enter the candidate set (D-08). Tests: `mcp_filters_never_resurrect_inaccessible_vault`, plus all pre-existing ACL tests green.
  </threat>
  <threat id="T-18-16" stride="Denial of Service" severity="low">
    Filtering forces one extra file read per candidate note (list: page of files; search: ≤50 capped hits — api.rs D-10 cap). Mitigation: bounded by the existing search cap and per-vault list sizes; read_note reuses the ACL helper (no double-walk). Accepted, documented in note_matches doc-comment.
  </threat>
  <threat id="T-18-17" stride="Tampering" severity="low">
    A malformed frontmatter page could panic the filter path (non-UTF-8, unterminated block). Mitigation: `crate::okf::frontmatter_of` returns None on any parse/UTF-8 failure ⇒ note simply doesn't match; no unwrap in the filter path. Tests: `list_notes_filter_by_type` fixture includes a no-frontmatter note; `list_notes_filter_type_and_tags_and` asserts empty-not-error.
  </threat>
</threat_model>
