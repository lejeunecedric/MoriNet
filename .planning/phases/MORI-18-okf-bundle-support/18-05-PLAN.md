<threat_model>
  <threat id="T-18-12" stride="Information Disclosure" severity="high">
    `?meta=1` could leak note content/metadata from vaults the token cannot access (richer response = bigger leak surface). Mitigation: meta branches reuse the SAME ACL-gated helpers (`source_dir` via list_notes/read_note) and the SAME 404 problem+json collapse BEFORE any frontmatter parsing; inaccessible never reaches the meta code. Tests: `api_meta_inaccessible_vault_404` (list AND read, identical 404 shape with and without meta).
  </threat>
  <threat id="T-18-13" stride="Tampering" severity="medium">
    A subtle default-path change (ordering, key set, content-type, ETag) silently breaks the v1.2 API contract (D-07 corrected: byte-identical defaults). Mitigation: meta is strictly `== "1"` opt-in; the bare-array pin test (:1149) is guarded as un-editable; new tests re-pin default shapes for list AND read. Tests: `api_list_notes_default_shape_unchanged`, `api_read_note_default_raw_markdown`, existing v1.2 suite green untouched.
  </threat>
  <threat id="T-18-14" stride="Denial of Service" severity="low">
    `?meta=1` on a large vault turns a list call into N file reads. Mitigation: list is already cursor-paginated (limit default 50, hard cap 200 — api.rs:333-334), so meta reads are bounded by the page size; read meta reads exactly one file. Accepted risk, documented in the handler doc-comment.
  </threat>
</threat_model>
