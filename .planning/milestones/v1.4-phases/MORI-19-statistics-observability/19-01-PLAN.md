<threat_model>
  <!-- ASVS L1 (config: security_asvs_level=1); gate blocks on HIGH severity. -->
  <threat id="T-19-01" stride="Information Disclosure" severity="medium">
    The new tables persist sensitive user data at rest: raw search query text, tool arguments (paths/slugs/queries) and response excerpts — note content a viewer might not otherwise see in bulk. Mitigation: excerpt/args are capped at 200 chars at every write site (enforced in 19-02/19-03; the schema has no full-body column at all — D-01 "full bodies NEVER stored"), 90-day prune (this plan, STAT-05), and reads are exposed ONLY through the owner/admin-gated Statistics sections (D-05, plan 19-04). Tests: prune tests pin the retention window; schema tests pin the CHECK vocabularies.
  </threat>
  <threat id="T-19-02" stride="Tampering" severity="medium">
    The first-ever table rebuild could silently lose history or indexes (a copy typo, a forgotten index) and degrade or skew every later stats query. Mitigation: explicit column-list INSERT...SELECT including id, both indexes recreated in the same file, sqlx's per-migration transaction makes the rebuild atomic (failure rolls back, boot fails loudly rather than half-migrating). Tests: access_log_accepts_all_three_sources, access_log_indexes_survive_rebuild, updated pin test access_log_rejects_bad_source.
  </threat>
  <threat id="T-19-03" stride="Denial of Service" severity="low">
    Unbounded growth of mcp_activity/search_queries (every MCP call + every search appends rows) bloats the SQLite file. Mitigation: bounded row shape (200-char caps), 90-day boot prune reusing the vault_changes convention (STAT-05), LIMIT on every read path. Tests: prune_mcp_activity_removes_only_old_rows, prune_search_queries_removes_only_old_rows.
  </threat>
</threat_model>
