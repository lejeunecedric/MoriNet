## Findings

| id | severity | file:line | description | suggested fix |
|----|----------|-----------|-------------|---------------|
| R-19-01 | MEDIUM | src/mcp.rs:407, 431–439 | Cross-vault excerpt leak on global MCP search. In `search_notes` with `slug=None`, `text` is the JSON of ALL hits across every accessible vault (`Hit { slug, path, line, snippet }` carries note paths + content snippets). The fan-out stores that same `text` as the excerpt on EVERY per-vault `mcp_activity` row. Scenario: user U has access to vault X (owned by O) and to vault Y that O cannot access; U runs a global search; the vault-X row's excerpt can contain vault-Y paths/snippets (whichever hits land in the first 200 chars of the JSON — vault iteration order decides). O then sees vault-Y content on vault X's Statistics page — exactly the "stats must not leak inaccessible vaults" rule (19-CONTEXT ACL pattern, D-05 intent). Bounded (200 chars × 20 rows) and requires a multi-vault sharing config, hence MEDIUM. The `Some(slug)` branch is safe (hits already scoped); REST `log_api_search` is safe (stores no excerpt). | In the `None` fan-out branch, serialize a per-vault excerpt: `hits.iter().filter(|h| h.slug == a.vault.slug)` before `serde_json::to_string` (or store an empty excerpt for global searches). Keep `resp_size` as the full response size if desired — the leak is only the excerpt. Add a pin: two vaults, global search, assert the vault-X row's excerpt contains no vault-Y path. |
| R-19-02 | LOW | src/store.rs:1443–1457 | `stats_per_day` keeps `LIMIT 90` while grouping by `(day, source)`. The source vocabulary grew from 2 (`web`,`mcp`) to 3 (`+api`), so a full 90-day window can produce up to 270 groups and the oldest days are silently truncated at 90 groups (~30 days shown). Pre-existing shape (already truncatable with 2 sources), but this phase made it likelier while touching the query anyway. | `LIMIT` scaled to the window (e.g. `days * 3` bound as a parameter) or drop the LIMIT since the `days` window already bounds rows (ceiling 90). |
| R-19-03 | LOW | src/store.rs:1569; src/mcp.rs:441 | `search_queries.query` is stored raw and uncapped (D-04 "raw query string"). REST trims but does not length-cap `q`; MCP stores `p.query` untrimmed and uncapped (bounded only by the request/URL size — axum's default 2 MB body limit on the MCP POST). A user can therefore persist multi-MB query strings per row for 90 days. Self-inflicted storage growth, viewer is owner/admin — accepted-tradeoff territory, but inconsistent with the 200-char discipline applied to args/excerpt. | Cap at the write site with `truncate_chars(query, 200)` (or trim + cap in `log_search_query`), and trim the MCP path to match REST. Update the two raw-query pins accordingly. |

WHERE ts < ...` cannot use `idx_*_slug_ts` (ts is not the leading column) → full-table scan at boot. Same convention as the pre-existing `prune_access_log`, and the tables are retention-bounded (90 days), so acceptable at this scale — noted for completeness under the "indexes on prune scans" focus. | Optional: add a `CREATE INDEX ... ON mcp_activity(ts)` / `search_queries(ts)` if row counts ever grow; otherwise document as intentional parity with `prune_access_log`. |

## Checked clean (no findings)

- **SQL safety**: every new statement in store.rs is fully parameterized, including `LIMIT ?` and the `datetime('now', ?)` modifier; `format!("-{days} days")` interpolates only a typed `i64`, and the HTTP boundary whitelists it to 7/30/90 (`stats_days`, server.rs:2822 — junk/`"7; DROP TABLE…"` → 90, pinned). No string-concatenated SQL anywhere in the diff.
- **Migration 0014 rebuild**: column-for-column identical to 0008 (only the CHECK vocabulary widened); explicit column-list `INSERT…SELECT` preserves ids; both original indexes recreated after rename; no triggers/views/FKs reference `access_log` (grep over migrations/); `AUTOINCREMENT` sequence continuity is correct (explicit-id insert updates `sqlite_sequence` for the new table before the old one is dropped); sqlx wraps each migration file in a transaction (default migrator, no `no_tx`), so the rebuild is atomic. Pin test `access_log_rejects_bad_source` moved to web|mcp|api in the same commit per D-07.
- **Best-effort logging (STAT-05)**: all four logging helpers (`log_access` callers, mcp `log_activity`/`log_search_query`, api `log_api_access`/`log_api_search`) clone owned data, `tokio::spawn`, and `let _ = …await` inside the task — no insert is awaited on a request path, no logging failure can alter a response. `log_api_search` does its fan-out DB read inside the spawn (one task). Stats-page reads (`recent_mcp_activity`, `top_search_queries`, `recent_search_queries`) use `unwrap_or_default`/match-fallback → empty state, never 500. Boot prunes in main.rs:157–164 are eprintln-guarded, cannot abort boot.
- **No probing trail**: every log call site sits strictly after the ACL gate (mcp read_note Ok/post-ACL decode-Err only; api_read_note after the 404-collapse; api_search Ok arm only) — pinned by `mcp_denied_call_logs_no_activity`, `api_denied_call_logs_nothing`, `api_search_requires_q_logs_nothing` (all re-run green).
- **XSS**: every untrusted field in the new sections is `html_escape`d — tool, args, email, status, excerpt (server.rs:3007 ff.), query text and top words (server.rs:3046 ff.), slug in chip hrefs; `html_escape` covers `& < > "` (safe in both text and quoted-attribute contexts); latency/size are `i64`; `ts` is not rendered. Pinned by `stats_mcp_activity_escapes_untrusted`.
- **ACL (D-05)**: sharee branch early-returns (server.rs:2903–2919) before `mcp_html`/`search_html` are even computed; sections live strictly inside the `entry.personal || is_admin` path; pinned by `stats_sharee_no_detailed_sections` (no section, no excerpt/query leak).
- **Privacy (STAT-05)**: full response bodies never stored — `resp_size` is a byte count, excerpt capped at 200 chars + ellipsis; `mcp_activity` has no column that could hold a body. (Cross-vault excerpt scoping is R-19-01.)
- **truncate_chars** (mcp.rs:147): `chars().take` — never byte-slices; `≤max` unchanged, else max chars + `…`; 0 → `…`; pinned by the é×300 UTF-8 test.
- **Resource issues**: spawns are bounded per call (search fan-out = 3 tasks per accessible vault, mirroring the pre-existing coarse `log_access` fan-out); `top_words` input capped at 200 queries; `StatsQuery` deserialization cannot fail or panic (single `Option<String>`); all `days` call sites updated (grep: only server.rs + tests call the four changed store fns).
