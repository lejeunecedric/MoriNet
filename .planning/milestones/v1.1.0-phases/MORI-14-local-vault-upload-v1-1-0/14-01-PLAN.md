<objective>
Local vault upload (LOCKED decisions D-01..D-06 in 14-CONTEXT.md): a signed-in user picks a directory in the browser (`webkitdirectory`), the markdown tree is POSTed as multipart to a new `POST /vaults/upload`, stored under `data_dir/uploads/<slug>/`, built through the shared `LocalSource` dispatch (AD-14) and registered with `create_personal_vault` — same locked gate, same quota, same slug rules as the GitHub load, and NO `vault_source` so Refresh keeps answering "no upstream to refresh". Security spine (D-03): strict filename sanitization with canonicalized prefix checks before any write; hard caps (D-02): 256 MB route-scoped body limit, 5 MB/file, 2000 files, abort-stores-nothing.

Maps to ROADMAP Phase 14 criteria and REQ-LOC-001 (picker + upload) / REQ-LOC-002 (owner-space storage + normal convert/build/register pipeline with quota + ACL identical to GitHub load).

Purpose: load a vault straight from the user's machine, no server-side path picking.
Output: `multipart` feature on axum, `upload_local_vault` handler + sanitizer + constants, uploads-dir cleanup in both delete flows, home-page "Local vault" form + locked-popup extension + picked-file-count JS, tests throughout.

Planner discretion calls (locked for the executor — 14-CONTEXT.md "Claude's Discretion"):
- **Route name**: `POST /vaults/upload` (D-01 already names it; keep).
- **Per-part read strategy**: STREAM each file part to disk via `field.chunk()` in a loop with a running byte counter (abort at >5 MB) — never `field.bytes()` (would buffer 256 MB in RAM).
- **Ignored-file handling**: silently skip `.git/` entries, dotfiles (any path segment starting with `.`) and non-`.md`/`.markdown` files — they are simply not written; no per-file report in the response (success is a redirect). The ≥1-markdown rule is the user-facing guard.
- **Top-level dir stripping**: split the client filename on `/`; if there are ≥2 segments drop the first (the picked directory name, e.g. `MyWiki/index.md` → `index.md`); a single bare segment (`file.md`, plain multi-file picker) is kept as-is.
- **Form layout**: second form inside the existing "Load a vault" panel, heading-free, fields `name` (text, required) + `files` (file input, `webkitdirectory multiple`, required) + submit "Upload vault".
- **Name is required** (no URL to default from, unlike the GitHub form).
- **Verified discrepancy**: the task brief said the delete flows "remove repo dirs" — they do NOT (server.rs:2024-2041 and :3085-3093 are DB-only; store `delete_vault` store.rs:527 is pure SQL). The uploads cleanup is therefore a NEW best-effort step in both handlers; do not add repo-dir deletion (out of scope).
</objective>
