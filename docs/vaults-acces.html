MoriNet — Vaults & accès

Schéma relationnel réel + qui accède à quoi · v0.1.7

Les trois tables

  • • users — email UNIQUE, password_hash (bcrypt), role CHECK IN ('admin','reader')
  • • vaults — slug UNIQUE, name, book_path (le dossier book/ compilé)
  • • vault_acl — table pivot (vault_id, user_id), PK composite, CASCADE des deux côtés
  • • vaults ne contient aucun champ de source : le type (local/github) est dans config.toml

Règle d'accès

  • • admin → voit et accède à tous les vaults, sans ligne ACL
  • • reader → seulement ceux avec une ligne dans vault_acl
  • • Le contrôle est appelé sur chaque lecture : UI web ET WebDAV
  • • PUT WebDAV = admin uniquement, même avec une ACL accordée
  • • /admin/browse = admin, et confiné à data_dir (403 si on sort)

Vault : cycle de vie

  • • Source local : dossier existant, build immédiat
  • • Source github : clone git2, re-sync + rebuild toutes les 5 min
  • • Contrat vault = book.toml + src/SUMMARY.md (mdBook natif)
  • • book_path pointe vers book/ — WebDAV expose le parent (= la source)
  • • Supprimer un vault → CASCADE efface ses lignes ACL

Authentification

  • • Web : cookie HMAC HttpOnly, 24 h, signature en temps constant
  • • WebDAV : HTTP Basic sur la même table bcrypt
  • • Email : tokens sha256, single-use (invitation 24 h, reset 1 h)
  • • Admin créé au boot via MORINET_ADMIN_EMAIL/PASSWORD

Ce qui change en Phase 8

  • • Aujourd'hui : 1 vault = 1 mdbook, servi sur /vault/<slug>/
  • • Demain : 1 livre par user, fusionné, cache sur disque
  • • La source de vérité reste vault_acl — seul le rendu change
  • • Un vault révoqué disparaît du livre au build suivant

Invariant de sécurité

  • • Aucun vault non-autorisé ne doit apparaître dans un livre
  • • Le chemin client est désencodé une seule fois, avant tout contrôle
  • • Sortir de la racine = refusé, jamais silencieusement ramené
  • • Ce sont des propriétés testées, pas des conventions
